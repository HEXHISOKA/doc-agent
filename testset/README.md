# 采购单据测试集（按业务域分组）

生成于 2026-10-25 16:09:25，模型 `deepseek-v4.1-flash`，OCR = RapidOCR(onnxruntime)，共 29 张。

## 先说清楚为什么重排

第一版找了 14 张「不同格式」的单据，其中 9 张是增值税发票、国外样例发票、航空行程单、零售小票——那是**财务报销与零售**，不是采购入库。拿它们测出来的「11 张拦截」里，至少 4 张是**假拦截**：发票本来就没有采购订单号、行程单本来就没有供应商、小票本来就没有数量单价。那不是系统发现问题，是喂错了数据。

「格式多样性」只有落在**同一个业务对象**上才有意义。所以现在分三组：

| 组 | 张数 | 是什么 | 通过/拦截 |
|---|---:|---|---|
| **a_hf_procurement** | 12 | 采购订单 + 收货单，HuggingFace 公开数据集，带字段级 gold，scan/photo 降质 | 7/5 |
| **b_cn_synthetic** | 8 | 中文自造：仿国内 ERP 打印样式 + 传真/复印退化 | 4/4 |
| c_offdomain | 9 | 旧网图，**不属于本业务域**，仅作反例留证 | 1/7 |

## B 组：中文自造（业务主场景）

公开渠道拿不到中文企业采购单据原件——这类文件含供应商报价与商业条款，不会公开。所以按国内 ERP 的打印样式自己造，并做了介质退化。

## 判定口径

| 词 | 含义 |
|---|---|
| **err** | 阻断级疑点，必须人工确认才能入库 |
| **warn** | 提醒级，不阻断（币种非人民币、含税口径、无价单据缺金额、无价单据却填了币种） |
| **通过** | 无 err |
| **拦截** | 至少 1 条 err |

**通过 ≠ 数据正确，拦截 ≠ 单据有错。** 前者只说明「没查到矛盾」，后者只说明「系统无法确认它对」。

## 这一轮发现并修掉的问题

| # | 问题 | 触发它的样本 | 修法 |
|---|---|---|---|
| 1 | 合计含税/含运费时，「明细之和=合计」必然不成立，原逻辑报 err 并建议**把含税总额改成税前小计** | A 组 4/6 张法式 PO（Total HT + TVA = TTC） | 差额落在 0.1%~25% 判为口径不同，只 warn、不给目标值 |
| 2 | 单价尾差（小数位被多读一位）时，建议「按 q×p 改金额」方向反了——该改的是单价 | A 组 3/6 张（如 60×6.426 vs 385.20，真实单价 6.42） | 相对差 <0.1% 时只提示核对单价，不给金额 |
| 3 | 收货单/装箱单本来没有金额，被当成「漏抽合计」拦截 | A 组 5/6 张收货单 | 明细全无价格信号 ⇒ 判为无价单据，只 warn |
| 4 | 有价单据丢日期却照样放行 | B 组 `cn_po_fax`（传真件日期整行没抽到） | 有价单据缺日期 ⇒ err |
| 5 | 「单价」这一格里装的其实是行金额（法语 PO 表头 `Montant` 被读进 `price`、`amount` 全空），老规则报的是「3 行缺金额」——**方向相反**，照做会把金额再乘一次数量 | A 组 `purchase_order_7732ff5b_photo`（gold 里该行 line_total 正是 137,58 / 125,79 / 120,00） | 让两个假设竞争解释合计：按「单价」算 Σ(数量×单价)是合计的 38681 倍，按「行金额」算 Σ金额 只差 9.5%（差额正是税与运费）⇒ 判定为装错格子，并把每个值作为「移到 amount」的候选给出 |
| 6 | 收货单的**件数合计**被填进金额栏（1650 = 550+550+550），而且四层校验全过：有编号、有供应商、有日期、合计是正数 | A 组 `goods_received_note_21664797_scan`（gold：`summary.total_accepted` = "1650"） | 合计非空但明细无任何价格 ⇒ 与数量之和比对；相等即判「这是件数的合计，不是钱的合计」，并说明该清空而不是改数 |
| 7 | 无价单据上凭空给出币种：5 张同来源的收货单（同为法语页面、同一批供应商）分别给出 CNY / CNY / EUR / USD / CNY | A 组 5 张 GRN + `cn_grn` + `en_packing_list` | 无金额 ⇒ 单据上不存在可读的币种标识，该值必然是推断；加 warn 提示不要当已核实字段下传 |

> 第 5、6 条的做法值得单独说一句：它们**没有引入单据类型分类**，而是让单据自己的数字说话。同一批数字在两种解释下必然有一种解释与表尾的合计吻合得多——「谁的误差小」就是判据。所以「把数量当金额」「把金额当单价」这种槽位错位，不需要知道这是采购单还是收货单也能判。真正需要分类的是**名称**槽位（见下面第 1 条）。

## 仍然存在的问题（如实记录）

1. **「收货方」与「供应商」抽反，规则层查不出来。**A 组那张收货单的 gold 是 `parties.issuer.name = Union Sports SAS`（开单方，也就是收货方自己）、`parties.supplier.name = Compete, Inc.`，而抽取结果把**收货方填成了 supplier**。这类错完全自洽——字段非空、没有矛盾、勾稽照样平——上面两条新规则能抓「数字装错格子」，抓不了「名称装错格子」。要判它，必须先知道「谁是买方」：采购订单的供应商是外方，收货单的供应商也是外方但开单方是自己。**这需要抽取前先分类、按类型选 schema**，本轮没做。
2. **一套 schema 灌所有单据类型，仍会逼出编造值。**金额栏为空时模型把数量当金额（规则 6 事后抓住）；币种栏无内容可读时模型编一个（规则 7 事后标记）。规则只能**事后抓**，不能**事前不产生**——正解仍是抽取前先分类。
3. **编号里的 O/0 混淆无法自动检出。**B 组 4 张中文单的编号 `PO20261025001` 全被 OCR 读成 `P020261025001`（字母 O → 数字 0），原始 OCR 词就是错的，模型照抄。历史画像机制能提示，但依赖历史库，本地为空时不触发。
4. **q×p 满足交换律，数量与单价互换查不出来。**B 组 `cn_po_tax` 首版把「2.5 吨 × 3200 元」抽成「3200 × 2.5」，乘出来还是 8000，勾稽通过。这类错误只能靠量级合理性（圆钢 3200 吨不合理）或单位字段发现，而 schema 没有 `unit`。
5. **模型会悄悄改精度。**`cn_po_tax` 的 OCR 明明读出 `2.5` 和 `0.5`（置信度 0.64/0.74），模型却输出 `qty=2` 和 `qty=1`。这次靠勾稽抓住了（2×3200≠8000），但如果该行金额也一起被改，就抓不住。
6. **同图重跑结果会变。**`temperature=0` 也不保证逐字一致，详见 `results/repeatability.json`（旧版数据）与 `results/hf_eval_all.json`。

## 复现

```bash
python src/fetch_hf_testset.py            # 从 HF parquet 抽样本 + 导出 gold
python src/eval_hf.py                     # A 组：跑链路 + 与 gold 比对
python src/gen_cn_po_variants.py          # B 组：生成中文单据（含传真/复印退化）
python src/probe_formats.py --dir samples/variants --only cn_po --out out/cn_po_probe.json
python src/check_slot_rules.py            # 槽位错位两条规则的回归测试（6/6）
python src/export_testset.py              # 导出本目录
```

> `extract` 是**一次运行的快照**。要判断某张图是识别错还是抽取错，先看 `results/ocr_text/` 里的文本，再看 `manifest.json` 的 `ground_truth`。

> 判定列由 `export_testset.py` 在导出时用**当前的** `validate.py` 重算，不是照抄跑图那一刻的结论。所以改了规则只要重跑导出，全表跟着更新——这样「规则版本」和「判定结果」不会各说各话。
