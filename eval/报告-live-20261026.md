## 零、为什么要重测

旧表的 A 列写的是「A：OCR → 文本」，测的是"把 OCR 文本发给模型抽字段"。
**这条链路现在已经不存在了。** 线上跑的是：

```
图片 → 去红章 → OCR → 版面重建 → 抽取 → 三层校验 + 出处校验
                                    ↓ 有疑点
                          自动发原图给视觉模型复核
                                    ↓ 模型给出可采纳的值
                              直接替换 → 重新校验
```

也就是说现在的 A 是「OCR + 不确认的大模型兜底」。旧表拿一个已下线的方案当结论，
继续挂在页面上会误导人。所以整份重测。

顺带把测量方式也换了：旧脚本在本地跑 OCR、用 `validate.py` 的精简副本校验；
新脚本**直接打线上部署的这一份代码**（`/api/ocr` → `/api/extract` → `/api/submit`
→ 存疑时 `/api/review`），校验结果是服务端自己算的，不复制、不重写。

## 二、先纠一个测量错误：单据编号这一列，旧表测不出来

这是本次重测最重要的发现，也直接推翻了旧表的核心论据。

### 2.1 现象

旧表说「单据编号准确率：A 100%、B 30%」，并据此得出"两条链路唯一的系统性差异在编号"。
但把旧报告 `report.json` 里的中间产物翻出来看：

```
历史 OCR 文本里编号第 2 位：字母 O = 0 条，数字 0 = 7 条（其余 13 条正则没匹配上）
历史抽取结果里第 2 位是字母 O：20 / 20
```

**OCR 一条都没读出字母 O，二十条全是数字 0；而抽取结果二十条全是字母 O。**

也就是说，那 100% 不是 OCR 读对了，是**抽取模型按提示词第 7 条把 0 改回了 O**：

> 7. 单据编号里的字母 O 与数字 0 在 OCR 中常被混淆，按上下文判断原始字符，不要静默改写。

这一条指令让模型做了一次"常识纠正"。真值恰好是 `PO…`，所以它对了，准确率显示 100%。

### 2.2 为什么说这批图上"本来就分不出来"

不是模型偷懒，是**图里没有证据**。这批样本的编号用 SimSun 渲染（`gen_eval_set.py` 里 `song` → `simsun.ttc`），
而 SimSun 里这两个字符的包围盒：

| 字号 | 字母 `O` | 数字 `0` | 宽度差 |
|---|---|---|---|
| 20px | 8 × 13（比 0.615） | 8 × 14（比 0.571） | **0 px** |
| 22px | 9 × 15（比 0.600） | 9 × 15（比 0.600） | **0 px** |
| 24px | 10 × 16（比 0.625） | 10 × 16（比 0.625） | **0 px** |

同宽、同高、同一个宽高比。真值 `PO2026092601` 只存在于生成脚本的字符串里，
像素上没有任何可判依据。

### 2.3 重测结果：旧表的差异消失了

| | 旧表（2026-10-24） | 新表（2026-10-26） |
|---|---|---|
| A 编号准确率 | 100% | **100%（O/0 视为同一字符）/ 40%（字面严格）** |
| B 编号准确率 | 30% | **100%（O/0 视为同一字符）/ 5%（字面严格）** |

换成同一把尺子量，两条链路**没有差异**。旧表那个 70 个百分点的差距，
量的是"模型愿不愿意猜"：

- A 看到的是纯文本，编号在文本里孤立出现，模型倾向按工业单据惯例写成 `PO` → 猜中 40%；
- B 看到的是图片，模型更信像素，照着画出 `0` → 猜中 5%。

**同一模型、同一天、同一批图，同一条指令，猜中的比例差了 8 倍，且都不由证据决定。**
这说明这个指标当时就不该按字面比。所以新表主判据把 `O/o` 与 `0` 视为同一字符，
另起一行给出字面严格率，用来交代差多少。

> 这不是给系统找台阶。旧表那 100% 是真的会掉的：同一份代码、同一条提示词，
> 隔一天重跑，A 的严格率从 100%（模型猜对）掉到 40%。靠模型猜出来的准确率，
> 换一次采样就没了。

## 四、自动放行为什么是 0

两列都是 0，但原因不同，且这个 0 比"75% 对 100%"更值得看。

**触发原因分布（A 列，20 张累计）：**

| 触发原因 | 次数 |
|---|---|
| 编号可疑（格式或出处） | **20** |
| 行金额勾稽不平 | 3 |
| 某字段读不出 | 2 |
| 合计与明细不符 | 1 |

20 张**每一张**都因为编号被标记为待复核。原因就是第二节那个 O/0：
OCR 读成 `P0…`，规则层（L2 历史格式）说"历史 12/12 条都是 PO 前缀，你这条差一个形近字符"，
出处层（L4）说"原文只能对上 92%，最接近的是 `p0…`"。

然后系统按设计发图复核。模型看图，**也读成 `0`**——因为图上没有 O 的证据。
于是复核给不出"可采纳的值"（`apply_value` 为空），疑点消解不了，这张单子就停在人工那里。

**这是"不确定就不放行"的直接代价，不是模型不准。** 值得记下来的是它的规模：
一个肉眼分不出的字符，让 20/20 全部转人工。真实单据如果也用这类字体/OCR 引擎，
人工率会同样高。

### 旧表的 60% 自动入库是怎么来的

旧表写「A 自动入库率 60%」，用的判据是 `validate_ok`。而当时 A 的编号被模型改成了 `PO`，
L2 那条格式规则**不报警**，所以既通过又没有待复核，直接放行。

也就是说：**旧表那 60% 的自动入库，依赖的正是"模型猜 O"这个不可靠动作。**
模型一不猜，60% 立刻归 0。

新表把判据改严了：自动放行 = `validate_ok` **且** 无待复核。
（旧口径也留着，在 `report_live.json` 的 `quad_loose` 里：A 15 放行 / 5 误放行，
B 20 放行 / 0 误放行——但那 5 张其实是"有疑点仍被算作放行"，不该算。）

## 五、兜底：精确，但救不了场

A 列独有的那一层，单独看：

| 项 | 数值 |
|---|---|
| 触发（需要看图复核的） | **20 / 20** |
| 模型给出可采纳的值 | 9 次 |
| 采纳后判对 | **9 次** |
| 采纳后判错 | **0 次** |
| 采纳后解除疑点 | **0 次** |
| 模型明确"没读到可采纳的值" | 11 张 |

两句话：

1. **精确率 100%（9/9）**。兜底没有制造任何新错误。这符合它的设计——
   `review.sanitize_findings` 里三条仲裁规则（数字写法差异判一致、形近字符不给建议、
   除非与规则建议互证）就是为了让人只能改"有第二判据支持"的字段。8~9 项全对，
   说明这套仲裁是有效的。
2. **解除率 0%（0/20）**。它改的字段（单价、金额、物料名）不是疑点的根因（编号）。
   根因在图上看不出来，所以改完再审，编号那条告警还在。

**兜底能修"读错了"，修不了"分不出来"。** 这两件事必须分开说，
否则很容易被理解成"加了兜底就自动了"。

## 六、成本反转：兜底触发率超过 34%，看图反而更便宜

这是这次重测里最反直觉的一条，也是选型时真正该看的。

把 A 的 token 拆开（`fallback.review_usage` 单独统计）：

| 项 | 每张 token |
|---|---|
| A 的抽取调用（纯文本） | **667** |
| A 的复核调用（图 + 文本 + 字段） | **2,014** |
| B 的直读调用（图） | **1,359** |

单看抽取，OCR 链路确实便宜：667 vs 1,359，**省 51%**。这也是 OCR 路线一直以来的卖点。

但兜底触发一次，就要多花 2,014。设触发率为 `p`：

```
A 的成本 = 667 + 2014 × p
B 的成本 = 1359
```

令两者相等：

```
667 + 2014p = 1359  →  p = 34.4%
```

- 触发率 **低于 34%**：OCR 链路更便宜（正常单据占多数时，这是常态）；
- 触发率 **高于 34%**：直接看图更便宜，而且还更准、更快。

这批样本的触发率是 **100%**，所以实测 A 的提示 token 是 B 的 **1.97 倍**（53,619 vs 27,185）。

端到端延迟同样：A 要 5.5 秒 OCR + 4.7 秒模型 = 9.9 秒；
B 只要 4.9 秒。**A 慢一倍，因为 OCR 是串在前面的一道固定开销。**

> 结论不是"OCR 没用"，是"OCR 的便宜是**条件性**的"。条件就是疑点率要低。
> 一旦系统对每张单都要求复核，OCR 就同时失去了成本、速度和准确率三个优势。

## 八、结论

1. **旧表"A 全面优于 B"的结论不成立。** 它的核心论据（编号 100% vs 30%）
   是一个测不出来的量：样本字体让 O 与 0 像素级同形，那个 100% 是模型猜的。
   换成 O/0 同字的判据后，两列都是 100%。
2. **真正的差异在明细：A 98.31%，B 100%。** OCR 的行列重建会把邻近单元格的字串在一起，
   直读没有这道环节。这一点旧表也测出来了，是对的。
3. **自动放行两列都是 0。** 不是哪条链路不行，是系统对"编号一个形近字符之差"
   一律要求人确认，而这批单 20/20 都踩中。
4. **兜底精确但不救场。** 9 次采纳全对，0 次解除疑点。它能补"读错"，补不了"分不出"。
5. **成本会反转。** 兜底触发率低于 34% 时 OCR 更便宜（667 vs 1359 token/张），
   高于 34% 时直读更便宜——而这批样本是 100%。

**如果让我现在选：** 面对这类"编号带字母 O、字体又区分不了"的单据，
直读更省事——更准、更快、更便宜。OCR 链路值得保留的理由是另外两条，
不是准确率：**单据不出内网**（OCR 在本地算，只有文本上云）和**疑点率低时省一半 token**。

**如果要把 A 这条链路救回来**，该动的不是模型，是规则：

- 编号里 `O/0`、`I/1` 这类形近差异，如果历史支持度足够高，应该**降级为不阻断**
  （现在是 warn 就触发复核，而复核在图上没有判据，必然空转）；
- 或者让人确认一次后记住（"这家供应商的编号就是 P0 开头"），别每张单都问一遍；
- 兜底只在"图上能读出证据"的字段上触发——现在它被编号拖着一起跑，
  20 次调用里 11 次是在做无用功。

## 九、怎么复现

```bash
cd outputs/doc-agent
python src/eval_live.py                      # 全量 20 张，约 6 分钟
python src/eval_live.py --limit 1 --chains A # 单张、只跑 A，先探通
```

脚本会打印每张的判定，最后写 `eval/report_live.json`。判定口径：

- `pass` = `validate_ok` 且 `needs_review=false`（服务端会直接放行的）
- `quad` = 四象限（放行且对 / 放行但错 / 拦截且错 / 拦截但对）
- `doc_no_norm` 与 `doc_no_strict` 分开记，差出来的就是"猜"出来的那部分

复现需要注意的两个坑：

1. `/api/*` 不带 `?sharecode=` 会被平台网关 403，请求根本到不了应用；
2. doc 缓存按会话隔离且每会话最多 8 张，20 张必须**逐张**上传-处理，
   不能先全传完再逐个提交。

## 十、局限（写在这里，免得被问出来）

1. **样本是合成的**，20 张，字体单一。真实扫描件的字体、压缩噪声、印章形态都比这复杂。
   尤其第二节那个"O 与 0 同形"，是 SimSun 的特性；换成思源黑体或印刷体，结论可能反过来。
2. **真值由生成脚本给出**，不是人工逐字标注。生成脚本写 `PO`，图上渲染成什么样它不管
   ——这正是第二节问题的根源。
3. **B 列走本地脚本调云通道**，不是线上接口。它和 A 用的是同一条通道、同一个模型，
   但少了线上服务端的 nonce 隔离与整段服务端编排（B 用的是同一份 `SYSTEM_PROMPT` 的图片版），
   严格说不是"线上 B"——线上没有 B。
4. **两次跑结果不同**（A 75%~80%，B 95%~100%）。20 张的样本量下，这是模型采样噪声，
   不是系统改动的效果。
5. **"自动放行"用 `commit=false` 判定，没有真写库**。真入库会留 20 条脏数据，
   而评测要的只是"会不会被放行"。

### 归因（每一条都有证据）

### 三、由此得到的两个诚实结论

1. **拦截数差 1~3 张是运行噪声，不是优劣**：同一链路（A）在 15:46 与 16:53 两次运行里
   分别放行 16 张和 19 张；退化集上 A 还比 B/C 少放行 1 张。把单次拦截数当成绩会被任何
   一次重跑打脸——**唯一在三套数据、多条链路、多次运行里稳定为 0 的指标是误放行**。
2. **上线版本的"最好"不在准确率，在完整度与可追责**：三条链路的 L2/L3/L4 与编号归一都走
   同一个 `/api/submit`，所以准确率必然并列。B/C 是评测探针——不落库、无审计哈希链、
   无追加更正、无导出。A 是唯一把「拦截原因 → 人工确认 → 入库 → 哈希留痕 → 事后逐格更正」
   这条闭环走完的链路。**准确率并列是刻意公开的消融证据，不是遮羞布。**

### 五、顺带修复的另一件事（本回合另一个需求）

入库前表格与更正表格里，改明细的**数量或单价**会自动算出**金额**并预填（标橙待确认），
人可直接改成别的值——一旦手改金额，`data-manual` 置位，后续不再被自动计算覆盖；
撤销数量/单价（双击）时金额回到"重新算"状态。服务端仍做类型与勾稽核对，自动算出的值
不会绕过任何校验。
